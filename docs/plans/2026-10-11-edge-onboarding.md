# Edge onboarding

**Status:** In progress. It revises [Edge remote
access](2026-09-27-edge-remote-access.md) and [Edge access
policies](2026-09-28-edge-access-policies.md); `docs/edge.md` and
`docs/teams.md` are updated with each phase.

**Goal:** Two people add one admin or member to a server through the edge
with one link and one click each. The app carries every secret. An admin's
stated intent is the decision and is asked for once. An admin on a tailnet,
SSH key or approved-device connection needs `sudo` for nothing the server
can verify itself. The edge stays transport and the server stays the
authority.

An **edge** is the sign-in service and relay that servers and clients dial
out to. An **account** is a person signed in to it with GitHub. A **device**
is one client install holding its own key; under `approved-devices` a new
one is **pending** until approved. A **claim** makes an account the
server's **owner** at the edge. An **invitation** names a GitHub account
that may join as a new member with a role. A **refusal** is the server's
answer to a connection it does not admit. A **join secret** is a random
value bound to one invitation and carried only in its link.

## 1. What is broken

As found in the code:

| | Today | Where |
| --- | --- | --- |
| 1 | A server whose first admin joined over tailnet or SSH key has members but no edge owner. A claim on it is refused with `RefusalClaimed` unless the admin first ran `aether member link`; otherwise the only bridge is `sudo aether-server edge claim-code --admin <member id>`, documented as console recovery | `claimServer`, `claimMember` in `internal/sshd/edge.go` |
| 2 | The edge records a server only once an account owns it. `aether invite` does not check for an owner before minting, so it reports success for an invitation nobody can receive | `EnrollServer` in `internal/edge/store/servers.go` updates and never inserts; `Service.Admit` answers `unknown server` (404) for a server with no row, and `Service.ReplaceDirectory` ignores an unclaimed server's directory (`internal/edge/service/access.go`) |
| 3 | `aether invite --github` tells the admin to send the server id, which it does not print | `cmd/aether/invite.go` |
| 4 | Approval codes, claim codes and server ids are generated by the product and carried by people over chat. The approval code reaches the joiner only inside a failed SSH handshake: `ssh: handshake failed … no supported methods remain`, then `server said:` | `refusalError` in `internal/cli/edge.go` |
| 5 | Nothing tells an approver that a device is waiting. A pending device is a row and a log line; no event reaches the dashboard, whose Needs you is run-centric | `edgeDevice`, `invitationDevice` in `internal/sshd/edge.go`; `web/src/lib/needs-you.ts` |
| 6 | Admin actions are split between `sudo` on the machine, a linked CLI and the dashboard. The desktop app can do none of the machine-side ones | `cmd/aether-server/edge.go` |
| 7 | Refusals reach clients as prose banners, and the dashboard classifies them by substring | `ssh.BannerError` throughout `internal/sshd/edge.go`; `edgeHop` in `web/src/store/sync.ts` |

## 2. Decisions

1. **Every edge-path refusal is structured.** The server sends it as the
   SSH authentication banner, the mechanism every refusal already uses: a
   first line `aether-refusal/1 <JSON>`, then the prose a renderer in
   `internal/edge/proto` produces for terminals. The JSON is a new
   `edgeproto` struct: a kind, plus the server name, device label, key
   fingerprint, account, the member and role it admits as, invitation id
   and bounds, and the approval code only where decision 9 allows.
   `internal/cli` parses the line and returns the struct as the error; its
   `Error()` is the prose with the exact next command, never wrapped in
   `ssh: handshake failed`. The local gateway puts the struct in the
   JSON-RPC error `data`, and the dashboard classifies by `kind`, replacing
   the substring checks in `edgeHop`. An unstructured banner from an older
   server keeps today's `server said:` rendering.
2. **Approval is by device id.** `member.device.approve` approves a device
   by id from an approved caller: an approved device, member SSH key or
   tailnet identity, under either policy, as `requireApprovedCaller` with
   `always` set already enforces. `code` becomes optional and, when given,
   must name the same device. Deny is `member.device.revoke`. The code no
   longer proves anything on an in-app approval: the approver is shown the
   device label, account, fingerprint, and the member and role it admits
   as, and clicks once. `member.device.list` carries the member and role
   for pending devices, as `member.device.lookup` does.
3. **A pending device is an event.** The server publishes `member.device`
   on the event stream when a device is recorded pending, approved or
   revoked, and the dashboard keeps its device list current from it. Needs
   you gains a card that is not a run, with **Approve** and **Deny**:

   | Viewer | Device | Card |
   | --- | --- | --- |
   | Admin | Waiting on an invitation | `<label> (github <login>) wants to join as <role>` |
   | Admin | A member's | `<label> (github <login>) signed in as <member>` |
   | Member | Their own | `New device <label> signed in as you` |

   The sidebar's Needs you count includes them.
4. **The server reports its edge.** A new `server.edge` control method
   returns the edge URL, server id, access policy, the owner's provider
   and login or none, whether it is connected, and whether the edge last
   reported it claimed. `aether invite` prints the server id from it; the
   dashboard's new Settings › Remote access section shows it.
   `member.invitation.create` and `member.identity.link` refuse on a server
   the edge has not recorded, because the edge relays nothing and keeps no
   directory for it, and name **Connect my GitHub account** and
   `aether edge connect`. An ownerless server the edge has recorded keeps
   relaying for its members and accepts both.
5. **Connect my GitHub account.** A new admin-only control method,
   `server.edge.claimcode`, accepted only from an approved device, member
   SSH key or tailnet identity, mints a claim code bound to the caller's
   member: the code `aether-server edge claim-code --admin <self>` issues,
   through `IssueClaimCode` with the admin set. It is refused while the
   server has an owner or the edge is off. The dashboard, through the
   local gateway (`edge.login` if not signed in, then `edge.claim` with
   that code), and `aether edge connect` use the code at once. The claim
   binds the signed-in GitHub account to the admin's member
   (`recoverAdmin`), approves the device, and the server reports `claimed`
   on its own control connection, so the edge's rule that an owner is
   recorded only from a claim connection opened for that account holds
   unchanged. `aether-server edge claim-code` without `--admin` refuses on
   a server with members and lists its admins, so a code that cannot work
   is never issued. Console recovery stays for an admin with no other way
   in.
6. **Invitations carry a join secret.** `member.invitation.create`
   generates it, stores its hash as `claim.json` stores the claim code's,
   and returns it once, in the link
   `https://<edge host>/join/<server id>/<invitation id>#<secret>`. The
   secret is in the fragment, so the edge never receives it. The joiner's
   client presents `join:<invitation id>:<secret>:github:<subject>` as the
   SSH user name once the host key has proved the id in the link, as
   `claim:<code>:…` does. The server compares in constant time against the
   hash, and only then matches the invitation to the account as today. An
   invited account connecting without the secret is refused with the kind
   that tells it to open the link. Under `account` that is the whole join.
   Under `approved-devices` the device is recorded pending on the
   invitation, with the bounds unchanged (10 per account, 10 per
   invitation); the joiner's app shows `Waiting for an admin of <server
   name> to approve this device` and retries until admitted. No code is
   shown and nothing is sent back. An invitation always names a GitHub
   account; there is no anonymous link.
7. **Join page and deep links.** The edge serves `GET
   /join/{server_id}/{invitation_id}` on the relay origin, with no session
   and no cookie. It opens
   `aether://join?edge=<relay origin>&server=<id>&invitation=<id>#<secret>`
   from a one-file script allowed by a page-specific `script-src 'self'`,
   shows the link text for pasting, and links the downloads. The fragment
   never reaches the edge over HTTP, but a compromised edge's script could
   read it; with a join secret that gains it nothing beyond what "What an
   attacker can do" in `docs/edge.md` already grants: under `account` it
   can already accept an open invitation for a login it forges, and under
   `approved-devices` the result is a pending device an admin must
   approve. There is no claim page: a claim secret read by a compromised
   edge would let it claim the server for its own account, so the claim
   link is the deep link only,
   `aether://claim?edge=<relay origin>&server=<id>#<secret>`. The desktop
   shell's `handleDeepLink` accepts `join` and `claim` beside `run` and
   hands them to the dashboard as `?join=` and `?claim=`. The Android shell accepts them the same way; the Android app
   reaches servers over a tailnet, not the edge, so its dashboard shows the
   link and the CLI command. The dashboard's Connect step accepts a pasted
   join or claim link, or a bare claim code.
8. **Setup prints a link.** `aether-server setup` prints the claim link in
   place of the bare code, with the same `<server id>-<secret>` inside it,
   and the `aether link --claim <code>` line for terminals.
9. **The approval code stays on the fallback paths only:** `sudo
   aether-server device approve <code>` and `aether device approve <code>`.
   A refusal carries the code only when the server sees no in-app
   approver: the device's member is the only admin and has no approved
   device. `aether device approve` also accepts a device id.
10. **The edge store does not change.** An ownerless server that was once
    claimed keeps its row and directory and keeps relaying for its members.
    A server the edge has not recorded is claimed by its admin through
    decision 5 before anyone is invited; decision 4 refuses earlier.

## 3. Flows

### Set up a server

Admin:

1. Runs `sudo aether-server setup`, chooses the access policy, and sees the
   claim link and the `aether link --claim <code>` line.
2. Opens the link on their computer, which opens the desktop app at the
   claim; without the app, they paste the link or run the
   `aether link --claim` line.
3. Signs in with GitHub if the app is not signed in, sees the account the
   claim is made for, and clicks **Claim and link**. The server makes them
   admin and owner and approves this device.

### Connect a server that already has an admin

Admin, on a tailnet, SSH key or approved-device connection:

1. Opens Settings › Remote access, which shows the edge, server id, policy
   and `owner: none`, and clicks **Connect my GitHub account**; or runs
   `aether edge connect`.
2. Signs in with GitHub if needed. The app mints the code with
   `server.edge.claimcode` and claims with it. The account is bound to
   their member, the device approved, and the server owned.

### Invite

Admin:

1. Runs `aether invite --github <login> --role <role>`, or uses Members ›
   Invite. A server without an edge owner refuses and names decision 5.
2. Sees the join link and the server id, and sends the link.

### Join under `account`

Joiner:

1. Opens the link. The page opens the app at the join.
2. Signs in with GitHub as the invited login. The app links the server,
   presenting the secret inside SSH, and opens the dashboard as the new
   member.

### Join under `approved-devices`

Joiner:

1. Opens the link and signs in as above.
2. Sees `Waiting for an admin of <server name> to approve this device`.
   The app retries until admitted, then opens the dashboard.

Admin: sees the card in Needs you (approve, below).

### Approve

Admin:

1. Sees `<label> (github <login>) wants to join as <role>` in Needs you,
   with the fingerprint, member and role in the card.
2. Clicks **Approve**, or **Deny** to revoke the device. The joiner's app
   is admitted on its next retry.

### Own-device approval

Member, on a new device:

1. Signs in with GitHub and links. Under `approved-devices` the device
   waits.

Same member, on an approved device:

1. Sees `New device <label> signed in as you` in Needs you, and clicks
   **Approve**.

### The fallback with a code

When the device's member is the only admin and has no approved device:

1. The refusal carries the approval code and `sudo aether-server device
   approve <code>`.
2. The machine's administrator runs it, sees what the code admits, and
   answers `y`.

## 4. Threat model deltas

Rows added to or changed in "Who must fail for access to be gained" and
"What an attacker can do" in `docs/edge.md`.

| Case | `account` | `approved-devices` |
| --- | --- | --- |
| Stolen GitHub account plus the join link | The whole join, as a signed-in invited account is today | A pending device; access also needs an admin's click after seeing device, account, fingerprint, member and role |
| Invited account without the link | Refused with the kind that names the link | The same; nothing is recorded |
| Edge forges a grant for an invited login | Refused without the secret, which the edge never sees | The same: not even a pending device |
| Edge forges a `claimed` report | Fails: an owner is recorded only from a claim connection opened for that account (rule unchanged) | The same |
| Edge serves the join page | The fragment never reaches the edge over HTTP. A compromised edge's script could read it and gains nothing more: it can already accept an open invitation for a login it forges | The same, and the result is a pending device an admin must approve. There is no claim page: a claim secret would give a compromised edge the server, so the claim link is the `aether://claim` deep link only |
| Own-device approval | Not needed | One click from an approved device of that member; a pending device still completes no handshake |
| `server.edge.claimcode` | Accepted only from an approved device, member SSH key or tailnet identity of an admin; a registered device cannot mint one | The same; a pending device cannot connect at all. The bar matches `member.device.approve` |
| Approval code | Unused | 40 bits; a code naming two waiting devices approves neither (`GetDeviceByApprovalCode`). Only on the fallback paths |

## 6. The GitHub signing-key check

`internal/scheduler/github.go` registers Aether's generated signing key
with `gh ssh-key add --type signing`, reads `gh ssh-key list`, and refuses
unless `listsFingerprint` finds the key's SHA256 fingerprint. Verified
against gh 2.x without a terminal:

| Command | Output |
| --- | --- |
| `gh ssh-key list` | `<title>\t<key type and base64>\t<created>\t<id>\t<type>`, no fingerprint, so the check never passes |
| `gh ssh-key add`, key already on this account | `✓ Public key already exists on your account`, exit 0 |
| `gh ssh-key add`, key on another account | GitHub answers 422 `key is already in use`; gh exits non-zero |

Fix: fingerprint each listed key and compare; make the stub in
`github_test.go` print what gh prints; say in the error that the
comparison concerns Aether's generated signing key, not the member's own
GitHub keys.
